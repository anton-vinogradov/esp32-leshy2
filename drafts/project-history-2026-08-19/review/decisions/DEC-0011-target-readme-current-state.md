# DEC-0011 — целевой README отдельно от текущего состояния

- Статус: **Принято владельцем проекта**
- Этап: сквозной контракт документации
- Дата принятия: 2026-08-16
- Затрагивает: оба репозитория, все последующие `DEC-*`, `REQ-*`, `REV-*` и release documentation

> Уточнено `DEC-0060` 2026-08-17: target README теперь проверяются именно как
> GitHub product landing pages. Review-ID chronology, maturity narrative и
> open-gate lists остаются только в current-state/ledger layers.

## Контекст

Корневые README обоих репозиториев до этого в основном описывали процесс перестройки и текущие блокеры. Такой вход честен для разработки, но не формирует по ходу работы цельный документ будущего готового продукта. Если смешивать цель и фактическое состояние на одной странице, принятое направление легко спутать с уже реализованной функцией.

## Решение

В каждом репозитории поддерживаются два разных входа:

1. Корневые `README.md` и `README.ru.md` — **целевой стартовый документ готового продукта**. Он постепенно собирает только принятые продуктовые контракты и описывает, каким должен стать законченный Leshy2.
2. `docs/status/current-state.md` и `docs/status/current-state.ru.md` — **текущее состояние проработки**: стадии, доказанное, открытые находки, ещё не принятые предложения, состояние реализации и следующий decision gate.

Ссылки двусторонние: target README ведёт в current state и канонический review ledger; current state ведёт обратно в target README обоих репозиториев.

## Граница авторитетности

- Каноническими остаются карточки `DEC-*`, `REQ-*`, `FND-*`, `REV-*` и таблица стадий hardware-репозитория.
- Target README — производный пользовательский обзор, а не самостоятельный источник принятия scope.
- В target README функция появляется только после принятого решения/требования. Открытое `IMP-*`, legacy-кандидат или неподтверждённая реализация туда не переносятся как свойство продукта.
- Принятая целевая архитектура может описываться до реализации, но верхний banner обязан явно говорить, что это target, а не заявление о текущей готовности.
- Current state может ссылаться на legacy и предложения, но явно отделяет их от принятых решений.
- Подробности не копируются между страницами: target объясняет продукт, current state — зрелость, ledger — доказательства.

## Контракт синхронизации

При каждом принятом решении проверяется:

1. меняет ли оно образ готового hardware-продукта;
2. меняет ли оно образ готового firmware-продукта;
3. меняет ли оно фактический статус/блокеры;
4. обновлены ли соответствующие EN/RU пары и cross-repository links;
5. не превратилось ли открытое условие в безусловное обещание.

Target и current-state страницы не обязаны повторять всю карточку решения, но обязаны ссылаться на канонический источник.

## Начальное состояние

На момент принятия решения target README уже включает принятые `DEC-0001`–`DEC-0010` в той мере, в которой они задают готовый продукт. Открытые `FND-0001`–`FND-0003`, `FND-0006`–`FND-0007` и `IMP-0010` остаются только в current-state/review слоях.
