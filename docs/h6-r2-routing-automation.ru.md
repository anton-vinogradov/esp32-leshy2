# H6 · Бенчмарк трассировки

[Главная](../README.ru.md) · [Текущие PCB](h6-r2-current-routing.ru.md) · [English](h6-r2-routing-automation.md)

**2026-09-20: одной командой с настройками по умолчанию получен проверенный результат UI 252 + RF 222 = 474/474 связи за 225,129 с**, включая исходную трассировку и три одинаковых холодных повтора каждого блока. Нарушения native DRC, соответствия схеме и границ участка — ноль; все 1 218 footprint, исходные файлы и невыбранная медь сохранены. Внутри команды модельных решений не было. [Измерения и свидетельства](../hardware/layout/benchmarks/2026-09-20-474-one-command-results.json).

Принята геометрия двух выбранных блоков. Каждый начинает с нулевой меди выбранных сетей; исходная медь вне этого состава остаётся окружением. Это **не** квалификация полных плат, электрических свойств, EMI, характеристик RF, ESD-топологии или производственной готовности. Рабочая трассировка приостановлена; H6 открыт, граница с прошивкой не меняется.

## Запуск

Из корня репозитория:

```sh
python3 tools/route_474.py
```

[Портфель повторов по умолчанию](../hardware/layout/h6-r2-474-repeat-portfolio.json) запускает два выбранных профиля, затем шесть новых холодных повторов. Этот запуск одной командой на подготовленном окружении прошёл все восемь попыток и финальную проверку хешей свидетельств.

Нужны подготовленные KRT/Python и native KiCad; переносимый установщик зависимостей **не включён**. Пути можно переопределить через `--engine-root` и `--engine-python`. Зафиксированная версия KRT и совмещённый патч NPTH/pending-pad описаны в [инструкции к патчам движка](../hardware/layout/engine-patches/README.md); совмещённый патч заменяет прежнее исправление только NPTH. Успешный UI-профиль: порядок bus, сетка 0,05 мм, стоимость via 75, вес эвристики 1,3, `endpoint_reservations_all`, `dense_first` и `pending_pad_protection`; RF использует `rf-target5`. Точные настройки находятся в портфеле.

До трассировки команда проверяет обе исходные копии через native KiCad. Каждый кандидат проходит независимые проверки геометрии, всех сетей и состава компонентов. Перед принятием результата повторно сверяются зафиксированные входы и пять хешей сохранённых свидетельств для исходных результатов и повторов. Только `status=pass`, `resolved=474` и код завершения 0 принимают оба блока; частичный результат не засчитывается. Вывод — короткий JSON с путём к итогу, подробные свидетельства остаются в `work/`. На macOS проверяемый запрет сна `caffeinate` действует во время расчёта и снимается при выходе; закрытие крышки или принудительный сон всё ещё могут приостановить ноутбук.

Прежняя последовательная оболочка для малых manifest сохранена; она использует [профиль подготовленного окружения](../hardware/layout/h6-r2-autorouter-profile.json):

```sh
python3 tools/route_board.py \
  --case hardware/layout/benchmarks/ui-inputs-service-id-82.json
```

Она пробует проверенный профиль, при провале добавляет альтернативы и требует три одинаковых повтора. Для изменённых исходников нужен заново проверенный manifest; устаревшие хеши отвергаются. Обе оболочки оставляют экспериментальную медь вне рабочих PCB.

## Приёмка проекта перед следующей пересборкой

```sh
python3 tools/check_design.py
```

Команда только читает проект и объединяет существующие аудиторы: десять реализованных ограниченных проверок и шесть обязательных областей, явно оставленных неквалифицированными. Прогоны с четырьмя native-процессами занимали **27–43 с** (последний — 43,472 с) при восьми рабочих слотах на этом ноутбуке с 12 логическими ядрами ([запись бенчмарка](../hardware/layout/benchmarks/2026-09-20-design-acceptance-results.json)); лимиты меняются через `--jobs` и `--native-jobs`. Проверяются `caffeinate`, состав и содержимое исходников, хеши свидетельств; отмена или тайм-аут останавливает принадлежащие запуску группы процессов. Команда не генерирует схемы, не меняет платы и не разрешает изготовление. Нужен подготовленный native KiCad Python; путь переопределяется через `--kicad-python`.

Текущие платы закономерно получают **`not_accepted`**, а не знак готовности: четыре ограниченных pass, два fail и десять unqualified. Не проходят предпосылки питания; полная native-связность показывает **UI 1 226 + RF 1 859 = 3 085** оставшихся связей независимо от обрезанных списков DRC. Полные модели выводов/состояний, электрические свойства меди, сборочная геометрия, производственное соответствие и измерения прототипа остаются обязательными. Свидетельства typed ERC проверяются по хешам, но этой командой ERC не перезапускается. Отсутствующие, устаревшие или неполные свидетельства не превращаются в PASS.

Коды завершения: **0** — все объявленные проверки прошли в своих границах; **1** — проект не принят; **2** — ошибка исполнения/свидетельств; **130** — отмена. Завершённые прогоны сохраняют границы проверок, замечания, хеши и время в уникальном `work/design-check-*/result.json`; ошибка запуска и отмена сообщают `report: null`, а не путь к старому итогу. Ожидаемый код 1 для незавершённого проекта не равен провалу регрессионного теста программы. Негативные тесты охватывают заявленную шину 5 В при установленном делителе на 3,222 В, пропущенные компоненты, устаревшие доказательства, неверный протокол, неполное покрытие, обрезанный DRC, отмену и оставленные дочерние процессы.

Движемся циклом **механизм → текущий проект → независимая валидация**, повторяя его перед переходом дальше. Этот первый шаг объединяет приёмку, но не доказывает полную электрическую правильность. Следующий изолированный пилот проверяет готовый локальный генератор схем по ограничениям на одной цепи индикатора; сгенерированные MPN и схема не становятся рабочими без проверки точных компонентов и независимой валидации. Внутри команды приёмки нет модельных решений; токены подготовки и полная окупаемость учитываются отдельно.

## Цена подготовки и неудачные попытки

Основная метрика затрат — **токены модели на полный проверенный результат**. Снимки журнала основной задачи дали примерно **157 тыс.**, **909 031** и, после возобновления работы, **199 005 токенов некэшированного ввода + вывода**. Это прокси подготовки/разработки, не биллинг и не цена изолированного повторного запуска. Второй интервал включает работу с ценами и документацией, последний — разработку, проверку, документацию и наблюдение за расчётом. Охват агентов не подтверждён, последующая работа исключена. Отсутствие модельных решений внутри команды не обнуляет подготовку. Полный повторный расход, экономия относительно прежнего метода и окупаемость ещё не измерены.

| Прежний эксперимент | Результат |
|---|---|

| Восемь исходных / восемь NPTH-исправленных холодных кандидатов | Полных pass нет; 330,6 / 269,5 с. Патч устранил наблюдавшиеся ошибки зазора до отверстий, но остались открытые связи и висящие via. |
| Повторы только RF / UI-пилот с rip-up | RF 222 прошёл; оба UI-кандидата оставили семь открытых связей. Восемь первых RF native-проверок аварийно завершились в ограниченной среде; те же кандидаты затем прошли вне неё без перетрассировки. |
| Первоначальный автоматический портфель | Провал за 875,0 с: RF прошёл повторы, все 16 UI-кандидатов отвергнуты; лучший чистый результат — две открытые связи. |

## Оставшийся рубеж

Подтверждённая владельцем цель — **холодная пересборка обеих полных плат** из схемы, выбранного размещения и проверенных ограничений/рецептов при каждом запуске, с автоматическим выполнением всех обязательных проверок. Дорожки прежней сборки не становятся входом трассировки; критические узлы воспроизводятся заново. Результат на 474 связях пока не доказывает этот процесс.

Далее: измерить модельный расход изолированного повторного запуска; проверить все классы сетей и оба движка, KRT и Freerouting; квалифицировать воспроизводимые группы RF/питания/кварцев/развязки по импедансу, току, возвратам и окружению; затем испытать полную пересборку после изменений размещения, схемы, footprint и правил. Рабочая политика по-прежнему покрывает лишь 342 из 3 085 оставшихся связей; 1 724 связи земли/питания находятся вне неё. Экспериментальный состав не снимает ограничения `manual_only`.

Сравнение предложенных компоновок интерфейсов/антенн через ограниченное размещение групп, трассировку и обязательные проверки остаётся планом. Смена платы для узла и числа слоёв требует отдельных архитектурных вариантов. Время полного цикла не измерено; ориентир владельца — 2 часа как отличный и 8+ часов как приемлемый результат. Возобновление рабочей трассировки требует доказанного процесса для обеих плат и всех классов, известного ручного остатка и электрической/механической квалификации. Неизвестный обязательный критерий блокирует принятие; плагин, локальная LLM и новый движок по-прежнему требуют измеренной необходимости и окупаемости.
